# API Pooling System — API Reference

## 1. Proxy API (for users of the system)

The proxy is a reverse proxy. Clients call it with their own key and the proxy
forwards to the underlying provider with the provider's key.

### Endpoint format

```
http://<proxy-host>:<port>/<provider>/<path>?<query>
```

| Part       | Description                                                        |
|------------|--------------------------------------------------------------------|
| `<provider>` | Provider name as configured by the admin (`add-provider --name`). |
| `<path>`   | Remaining path, appended to the provider's base URL.              |
| `<query>`  | Query string, forwarded unchanged.                                |

Examples:

```
POST http://localhost:8080/openai/v1/chat/completions
POST http://localhost:8080/anthropic/v1/messages
GET  http://localhost:8080/gemini/v1beta/models
```

If the provider's base URL is `https://api.anthropic.com`, then a request to
`/anthropic/v1/messages` is forwarded to
`https://api.anthropic.com/v1/messages`.

### Authentication

Send the **user key** (generated by the admin via `generate-key`) in either form:

```
Authorization: Bearer <user-key>
```

or

```
X-API-Key: <user-key>
```

The proxy replaces it with the provider's key before forwarding — user keys are
never sent upstream.

### Streaming (SSE)

Responses are relayed as a live stream. For `text/event-stream` (chat
completions, streaming, SSE) each event/chunk is forwarded to the client as
soon as the provider produces it — clients see the first token immediately
instead of waiting for the full response. Request bodies are still read fully
first so the proxy can retry another provider key on failure.

### Response codes

| Code | Meaning                                              |
|------|------------------------------------------------------|
| 200  | Success (body relayed from provider)                 |
| 400  | Missing provider in path, or unreadable body         |
| 401  | Missing / invalid / expired / revoked user key       |
| 403  | IP blocked by bot protection                         |
| 404  | Unknown provider                                     |
| 429  | Rate limit exceeded (per IP or per user key)         |
| 502  | All provider keys failed (network errors)            |
| 503  | Provider inactive or no active keys for provider     |

Errors are returned as JSON:

```json
{ "error": "invalid api key", "status": 401 }
```

### Example

```bash
# admin generates a key
java -jar java-admin/target/api-pool-admin.jar generate-key --user alice --tier premium

# user calls the proxy
curl -X POST http://localhost:8080/openai/v1/chat/completions \
  -H "Authorization: Bearer pkay_..." \
  -H "Content-Type: application/json" \
  -d '{"model":"gpt-4o","messages":[{"role":"user","content":"Hi"}]}'
```

## 2. Admin CLI

Run from the project root (the working directory must contain `config.json`):

```bash
java -jar java-admin/target/api-pool-admin.jar --cli        # interactive REPL
java -jar java-admin/target/api-pool-admin.jar --tui        # menu-driven TUI
java -jar java-admin/target/api-pool-admin.jar <command>    # one-shot
```

### Quick start

Providers are **third-party** endpoints (resellers with OpenAI-compatible APIs)
— the system accepts any base URL, and model lists are defined by the admin
(`add-model` one by one, or `import-models` to upload a whole list at once).
`database/models.json.example` shows the file format.

```bash
# 1. login (first run creates admin/admin from config.json)
java -jar java-admin/target/api-pool-admin.jar login --username admin --password admin

# 2. add a (third-party) provider - any OpenAI-compatible base URL works
java -jar java-admin/target/api-pool-admin.jar add-provider --name openrouter --url https://openrouter.ai/api/v1
# 3. upload the model list yourself (JSON or one-per-line text file)
java -jar java-admin/target/api-pool-admin.jar import-models --provider openrouter --file database/models.json.example
java -jar java-admin/target/api-pool-admin.jar add-key --provider openrouter --key sk-or-...

# 4. create a user and generate their key
java -jar java-admin/target/api-pool-admin.jar add-user --username alice --password secret --tier premium
java -jar java-admin/target/api-pool-admin.jar generate-key --user alice --tier premium
```

### Command reference

| Command | Description |
|---------|-------------|
| `login --username <user> --password <pass>` | Login as admin (token valid 7 days) |
| `logout` | Logout |
| `add-provider --name <name> --url <url>` | Add a provider |
| `add-model --provider <name> --model <model>` | Add a model to a provider |
| `add-key --provider <name> --key <api-key> [--model <model>] [--auth-header <header>]` | Add a provider API key (auth header defaults to `authorization`/Bearer; use `x-goog-api-key` for Gemini) |
| `import-models --provider <name> --file <path>` | Bulk-upload models for a provider from a JSON file (array of strings, array of `{"name": ...}` objects, or `{"models": [...]}`) or a plain text file (one model per line) |
| `remove-provider-key --key <api-key>` | Remove a provider key |
| `list-providers` | List providers and their models |
| `list-provider-keys` | List provider keys |
| `add-user --username <user> --password <pass> [--email <e>] [--tier <t>]` | Create a user |
| `list-users` | List users |
| `set-tier --user <user_id> --tier <tier>` | Set a user's tier |
| `delete-user --user <user_id>` | Delete a user |
| `generate-key --user <user_id> --tier <tier>` | Generate a user key (`pkay_...`, expires per config) |
| `list-keys` | List all user keys |
| `revoke-key --key <key>` | Revoke a user key |
| `system-info` | Show system information |
| `dashboard` | Show dashboard (counts + recent logs) |
| `logs` | Show recent log entries |
| `help` | Show help |

`--user` accepts either the user id or the username where noted.

## 3. Admin HTTP API (deployed instance)

The proxy exposes a JSON admin API under `/admin` so the deployed instance can
be managed remotely. Auth: `POST /admin/login` returns a session token; all
other endpoints require `Authorization: Bearer <token>` (token lasts
`admin.token_duration_days`, default 7). Credentials come from the `admin`
section of `config.json`, overridable with the `ADMIN_USERNAME` /
`ADMIN_PASSWORD` environment variables.

| Method & path | Body | Description |
|---------------|------|-------------|
| `POST /admin/login` | `{"username", "password"}` | Login, returns `{"token", ...}` |
| `POST /admin/logout` | — | Invalidate the current token |
| `GET /admin/providers` | — | List providers with models + masked keys |
| `POST /admin/providers` | `{"name", "url"}` | Add a provider |
| `DELETE /admin/providers/{name}` | — | Delete a provider (and its keys/models) |
| `POST /admin/providers/{name}/keys` | `{"key", "auth_header"?}` | Add a provider key (`auth_header` e.g. `x-goog-api-key`) |
| `DELETE /admin/providers/{name}/keys/{id}` | — | Remove a provider key |
| `POST /admin/providers/{name}/models` | `{"models": [...]}` | Import models (strings or `{"name": ...}` objects; duplicates skipped) |
| `GET /admin/users` | — | List users with masked keys |
| `POST /admin/users` | `{"username", "password", "tier"?}` | Create a user |
| `POST /admin/users/{name}/keys` | `{"tier"?, "max_limit"?}` | Generate a user key (returned once) |
| `POST /admin/keys/revoke` | `{"key"}` | Revoke a user key |
| `GET /admin/stats` | — | Counts (users, keys, requests) + recent logs |

All responses are JSON; errors look like `{"error": "...", "status": 401}`.
Provider keys and user keys are masked in list responses (e.g. `sk-or-…abcd`);
generated user keys are shown in full exactly once.

```bash
# quick example
curl -X POST https://<host>/admin/login -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"..."}'
curl -X POST https://<host>/admin/providers -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: application/json' -d '{"name":"openrouter","url":"https://openrouter.ai/api/v1"}'
```

## 4. Deployment (Railway)

The proxy is deployable as a container (`Dockerfile` at the repo root,
`railway.json` configures the health check). Deploy with the Railway CLI:

```bash
railway init --name <project>
railway up -y -d --service <service>
railway domain          # get the public URL
```

Environment variables:

| Variable         | Purpose                                              |
|------------------|------------------------------------------------------|
| `PORT`           | Listening port (Railway sets this automatically)     |
| `DATABASE_PATH`  | SQLite file location, e.g. `/data/db.sqlite` for a Railway volume |
| `ADMIN_USERNAME` | Admin username for `/admin` API (default: `admin`)   |
| `ADMIN_PASSWORD` | Admin password for `/admin` API (default: `admin` — set this in production!) |

`GET /health` (no auth) returns `{"status":"ok"}` and is used by the platform
health check.

> The deployed instance is managed entirely via the admin HTTP API above — it
> has its own database on the volume, separate from the local CLI's.
